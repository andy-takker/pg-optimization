# ДЗ 8. Схема данных: ускорение аналитики на Chicago Taxi (10 ГБ) + 300 партиций

Финальная работа курса. Загрузка набора Chicago Taxi (~10 ГБ CSV, ~26.8 млн строк) и ускорение аналитического запроса разными способами, плюс задание со * — деградация на 300+ партициях. Подтверждает и расширяет находку про JIT из [hw03](../hw03/).

## 1. Стенд и данные

| Компонент | Значение |
|---|---|
| ВМ | GCP e2-standard-4 (4 vCPU, 16 ГБ), europe-west1-b, pd-ssd 100 ГБ |
| ОС / СУБД | Ubuntu 24.04 / PostgreSQL 18.4 (PGDG), конфиг курса (shared_buffers 4 ГБ, parallel 4) |
| Данные | `gs://chicago10` (43 CSV) через **gcsfuse**, таблица `taxi_trips` = **26 753 683 строки, 11 ГБ** |

Целевой запрос (доля чаевых по типу оплаты):

```sql
SELECT payment_type, round(sum(tips)/sum(tips+fare)*100) tips_percent, count(*)
FROM taxi_trips GROUP BY payment_type ORDER BY 3 DESC;
```

## 2. Способы ускорения

| Способ | Время | Ключевая деталь |
|---|---|---|
| Seq Scan, JIT on (базлайн) | **8.6 с** | Parallel Seq Scan, ~933k блоков с диска; ~2.9 с из них — JIT |
| Seq Scan, JIT off | 3.8 с | JIT на этом запросе только вредит |
| Index Only Scan, **до** VACUUM ANALYZE | 7.5 с | **Heap Fetches: 5 815 723** — visibility map не выставлена |
| Index Only Scan, **после** VACUUM ANALYZE | 4.5 с | **Heap Fetches: 0** — читает ~1.1 ГБ индекса вместо 11 ГБ таблицы |
| **matview (преагрегат)** | **2.2 мс** | размер 24 КБ; **×3800** быстрее базлайна |

![способы ускорения](images/speedup_ways.png)

- **Покрывающий индекс `(payment_type) INCLUDE (tips, fare)` сам по себе почти не помогает** (7.5 с): после массовой загрузки visibility map пуста → Index Only Scan делает 5.8 млн обращений к куче. **Только `VACUUM ANALYZE` обнуляет heap fetches** и даёт чистый Index Only Scan (4.5 с) — это ровно тот инсайт, что прямо написан в документации и показан в лекции.
- **Преагрегат (matview) — лучший ответ для повторяемой аналитики**: отчёт из 11 заранее посчитанных строк за **2.2 мс**. Цена — пересчёт matview (обновление — тема занятия 10).
- Создание индекса 68 с, VACUUM ANALYZE 68 с, построение matview 3.5 с.

## 3. Задание со * — 300 hash-партиций

Перелили 26.8 млн строк в таблицу с **300 hash-секциями** и прогнали тот же агрегат (он уходит **во все** секции):

| Конфигурация | Время | Planning | JIT-функций |
|---|---|---|---|
| непартиционир., JIT off | 3.8 с | — | — |
| непартиционир., JIT on | 8.6 с | 0.9 мс | 48 |
| 300 партиций, JIT off | **38.5 с** | 53 мс | — |
| 300 партиций, JIT on | **66.9 с** | 45 мс | **3038** |

![JIT на партициях](images/jit_partitions.png)

- **Секционирование сделало агрегат во все секции в ~10 раз МЕДЛЕННЕЕ** (38.5 с против 3.8 с непартиционированной при jit off): Parallel Append обходит 300 секций, накладные расходы перевешивают.
- **JIT на 300 секциях — катастрофа**: планировщик компилирует код для **каждой** секции → **3038 функций** (против 48 на одной таблице, ×63), что добавляет **+28 с** к запросу (66.9 vs 38.5 с). Прямое продолжение находки [hw03](../hw03/), на которую ссылается лектор.
- Операционная цена: перелив 26.8 млн строк в 300 секций — 3.5 мин, `VACUUM ANALYZE` 300 секций — **8 минут**.

## 4. Выводы

1. **Индекс на OLAP-агрегате бесполезен без `VACUUM ANALYZE`** — он выставляет visibility map (heap fetches 5.8 млн → 0) и обновляет статистику. После массовой загрузки — обязателен.
2. **Преагрегат (matview) — чемпион повторяемой аналитики**: ×3800 (2.2 мс vs 8.6 с). Для разовых запросов — покрывающий индекс (×1.9 после VACUUM ANALYZE).
3. **JIT вредит этому аналитическому запросу**: даже на одной таблице 8.6 → 3.8 с при `jit=off`; на сотнях секций JIT компилирует тысячи функций и убивает производительность — `jit=off` обязателен при многих партициях.
4. **Секционирование — не «ускоритель аналитики»**: запрос-агрегат во все секции на 300 партициях в ~10 раз медленнее одной таблицы. Партиционировать стоит, только если запросы уходят в одну/несколько секций (pruning) — иначе антипаттерн.
5. Для тяжёлой OLAP-аналитики правильные инструменты — преагрегаты/matview, покрывающие индексы, колоночное хранение (cstore/ClickHouse), а не «больше партиций» или «больше индексов».
